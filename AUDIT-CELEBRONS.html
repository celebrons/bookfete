Conclusion en une phrase

Le problème de cohérence des livres n'est pas un problème de prompts : c'est l'absence des étapes intermédiaires. Le plan de chapitre et le contrôle qualité existent sous forme de fonctions vides, et la génération reçoit les témoignages bruts concaténés. La bonne nouvelle : le moteur de prompts versionnés (promptEngine.js) est solide et constitue une base saine — la refonte consiste à remplir l'architecture, pas à la remplacer.

01 Architecture actuelle

Monolithe classique en trois blocs, déployé sur Render. Aucune infrastructure superflue — c'est un point positif à préserver.

┌─────────────────────────────────────────────────────────────────┐ │ FRONTEND — React 18 + CRA/craco (bookfete-front.onrender.com) │ │ Thème « Luxe » maison, React Router 6, pas de state manager │ └───────────────┬─────────────────────────────┬───────────────────┘ │ fetch REST │ supabase-js (clé anon) │ (~10 bases URL dupliquées) │ ÉCRITURES DIRECTES ▼ ▼ ┌───────────────────────────────┐ ┌─────────────────────────────┐ │ BACKEND — Express (:5001) │ │ SUPABASE │ │ service_role key → RLS │──▶│ PostgreSQL · Auth · Storage│ │ contournée │ │ 11 tables │ └───────┬───────────────────────┘ └─────────────────────────────┘ │ ├──▶ Mistral API (mistral-small-latest, 100 % des appels) ├──▶ Stripe (webhook + machine à états commandes) ├──▶ SendGrid/Nodemailer └──▶ PDF : Chrome headless (execFile) ── fallback ──▶ PDFKit

Architecture Double chemin d'écriture

Le frontend écrit directement dans Supabase avec la clé anon (contributions, chapters, books, chapter_invites, book_contributors) pour une trentaine d'opérations, en parallèle du backend qui utilise la service_role et contourne donc RLS. Deux chemins d'écriture pour les mêmes données : la cohérence métier ne peut être garantie côté serveur, et la sécurité repose entièrement sur des policies RLS que le backend ignore.

Recommandation : ne pas traiter ce point dans la refonte éditoriale (hors périmètre), mais figer la règle : toute nouvelle écriture passe par le backend. Les lectures directes peuvent rester.

03 Fonctionnement actuel de la génération IA

Le moteur de prompts

Tous les appels passent par promptEngine.runPromptGeneration(). Le contenu des prompts n'est pas dans le code : il est stocké dans la table prompt_templates, versionné, avec un seul enregistrement status='active' par type (contrainte d'unicité partielle en base). Le moteur :

  1. charge le template actif (cache mémoire, TTL 30 s) ;
  2. compile context_block + data_block avec un mini-moteur de templates maison ({{var}}, {{#each}}, {{#if}}, {{#if (eq a "b")}}) ;
  3. refuse de partir s'il reste un placeholder non résolu — bonne pratique ;
  4. appelle Mistral, puis valide la sortie : nombre de mots min/max, phrases interdites, absence de placeholders, sortie non vide ;
  5. en cas d'échec, relance jusqu'à 2 fois avec un prompt de correction listant les règles violées ;
  6. journalise chaque tentative dans prompt_generation_logs.

À conserver Ce moteur est un vrai actif

Prompts hors du code, versionnés, avec validation automatique, retry auto-correctif et journalisation : c'est exactement l'infrastructure dont la V2 a besoin. Il ne faut surtout pas le remplacer — il faut y ajouter deux types de prompts et le mode JSON.

Comment les témoignages arrivent au modèle

C'est ici que se situe la cause racine. buildChapterBodyPromptVariables() (books.js:1990) construit les variables du prompt chapter_body : 

// books.js — les contributions partent brutes, en double format
contributions:      promptContributions,   // [{name, role, response_text}] — 5 000 car. chacune
contributions_text: contributionsText,     // "Nom (rôle) : message…" concaténé, 700 car. chacune
contributions_count: 25,
contributions_richness: "…"

Ce qui est transmis : tous les témoignages approuvés du chapitre, tronqués, concaténés. Ce qui n'est pas transmis :

  • aucune extraction structurée (personnes, dates, lieux, anecdotes, faits) ;
  • aucune sélection par pertinence — chaque chapitre reçoit tout ce qui lui est rattaché ;
  • aucun registre partagé entre chapitres : le seul lien inter-chapitres est previousChapterSummaries (résumés des chapitres déjà validés) et les titres voisins ;
  • aucune liste de faits interdits ou d'éléments inconnus.

Le modèle doit donc, en un seul appel, lire 25 témoignages, décider quoi retenir, à qui l'attribuer, comment l'articuler, et rédiger 8 pages. Les répétitions, mélanges d'anecdotes et attributions erronées en découlent mécaniquement.

Dette Variables dupliquées en trois conventions

La fonction renvoie chaque valeur en snake_case, en camelCase, et parfois en tout-minuscule : contributions_text, contributionstext, contributionsText — soit ~60 clés pour ~30 valeurs. Symptôme d'une incertitude sur la convention utilisée par les templates en base. À unifier lors de l'extraction (une seule convention, snake_case, alignée sur les templates existants).

04 Ce qui est bon et doit être conservé

01 Le moteur de prompts versionnés

promptEngine.js — prompts en base, versionnés, un seul actif par type, validation de sortie, retry auto-correctif, journalisation. Fondation de la V2.

02 Le workflow de chapitre en 4 étapes

Amorce → Contribution → Invitations → Clôture, avec état de chapitre, modération des contributions (approved, needs_revision, moderation_feedback) et demande de révision adressée au contributeur. L'étape G de la cible existe déjà en grande partie.

03 La configuration par type d'événement

book_configs couvre déjà 7 familles d'événements avec des champs dédiés. Pour le cas de référence « pot de départ », tout est en place : years_in_role, job_description_plain, will_be_missed_for, contributor_circle, retirement_project, departure_context, time_together, next_destination. Aucune migration de schéma nécessaire pour l'étape 9 de ta feuille de route.

04 Les contributions originales sont préservées

L'exigence « ne jamais remplacer le texte original » est déjà respectée : le texte brut reste dans contributions.message et les brouillons IA sont stockés séparément. Le principe est acquis, seul le mécanisme de stockage est à corriger (§05).

05 Le repli déterministe sans IA

buildFallbackChapterDraft() produit un chapitre complet et structuré sans aucun appel modèle. Précieux pour les tests, les démonstrations et la résilience — c'est ce qui a permis de figer des snapshots de rendu aujourd'hui.

06 La chaîne commande & paiement

orders avec machine à états à 10 positions (draft → awaiting_payment → paid → pdf_generating → pdf_ready → print_queued → sent_to_printer → printed → shipped → delivered), webhook Stripe sur route brute avant express.json(), contrôle d'accès au PDF selon le statut de commande. Hors périmètre de la refonte, à ne pas toucher.

Dette structurelle

Modèle de données Les brouillons sont stockés dans de fausses contributions

Il n'existe aucune table de brouillons. L'état d'un chapitre et son texte généré sont écrits dans la table contributions, sous des adresses e-mail sentinelles, avec du JSON dans le champ message : 

CHAPTER_DRAFT_EMAIL = '__chapter_draft__@system.local'  // message = JSON.stringify(draftState)
CHAPTER_STATE_EMAIL = '__chapter_state__@system.local'  // message = 'closed'

Conséquences : tout code qui lit les contributions doit filtrer ces lignes (le filtre est dupliqué dans buildChapterDraftSourcePayload, inviteController, et côté frontend) ; aucun historique de versions ; aucune contrainte d'intégrité ; les compteurs de contributions sont faussés si un filtre est oublié. C'est le principal obstacle aux étapes B à F, qui ont besoin d'un vrai modèle éditorial.

Maintenabilité routes/books.js : 6 550 lignes, 128 fonctions

Un seul fichier contient le CRUD, la génération de brouillons, l'orchestration IA, la logique de commande, le rendu HTML, la génération PDF et 1 110 lignes de CSS d'impression dans un template literal (getPrintableBookStyles). Toute modification du pipeline éditorial passe aujourd'hui par ce fichier.

09 Architecture V2 proposée

Principe directeur

La garantie « aucun fait inventé » ne doit pas reposer sur le modèle. Elle doit être vérifiée mécaniquement : tout nom propre, toute date, tout lieu du texte généré doit se retrouver dans un registre construit à partir des contributions originales. Sinon, c'est une invention — détectée par du code, sans appel IA, de façon déterministe et testable.

Trois nouveaux types de prompts

À ajouter dans la contrainte CHECK de prompt_templates.type et dans TEMPLATE_TYPES. Les 8 types existants restent intacts.

contribution_analysis
Étape B — extraction JSON stricte d'un seul témoignage. Petit prompt, petite sortie, mistral-small.
book_plan
Étape D — construction du plan à partir du registre d'entités (jamais des textes bruts). Le seul endroit où le raisonnement compte : candidat à mistral-large-latest.
chapter_correction
Étape F — correction ciblée d'un chapitre à partir de la liste des violations détectées.

Deux évolutions du moteur existant

  1. Mode JSON natif. Ajouter response_format: { type: 'json_object' } dans runPromptGeneration quand le template le demande (nouvelle colonne output_mode). Fiabilise l'étape B et rend aiOutputContracts.js moins acrobatique.
  2. Comptabilité des appels. Ajouter prompt_tokens, completion_tokens, model, duration_ms à prompt_generation_logs. La réponse Mistral porte déjà l'objet usage. Sans cela, « optimiser le coût API » n'est pas mesurable.

La V2 coûte plus cher au premier passage (+27 appels de mistral-small sur des entrées courtes, soit quelques centimes) et moins cher dès la deuxième itération, parce que l'analyse n'est jamais rejouée et que la régénération d'un chapitre n'entraîne plus celle des autres. Le vrai gain reste la qualité : chaque appel reçoit un contexte restreint et pertinent au lieu de 25 témoignages concaténés.

Ce que la V2 ne fait pas

Conformément à ton §5 — pas de microservices, pas de Kubernetes, pas de nouvelle base, pas de base vectorielle, pas de RAG, pas de changement de stack frontend, pas de nouvelle infrastructure. Tout tient dans : 6 tables Supabase, 3 templates de prompt, un dossier services/editorial/, et un validateur en JavaScript pur.

Mode collecte libre pour le pot de départ

Changement de produit à valider avec toi. Aujourd'hui l'invitation cible un chapitre précis (chapter_invites.chapter_id) : le contributeur répond à un thème décidé d'avance. Ton §9 décrit l'inverse : 20–30 témoignages libres, puis le plan construit les chapitres.

Question ouverte à trancher avant l'étape 07

L'étape 11 n'est pas un détail technique : elle décide si Celebrons demande au créateur de définir les chapitres avant la collecte (modèle actuel, qui guide les contributeurs et produit des témoignages plus ciblés) ou de laisser l'IA les découvrir après (modèle de ton §9, plus simple pour les invités mais qui repose entièrement sur la qualité du plan). Les deux se défendent, et l'architecture proposée les supporte tous les deux — mais le choix conditionne la forme du template book_plan. À décider avant l'étape 07.
